# راه‌اندازی لایه پشتیبان و احراز هویت پنل RLS

این پیاده‌سازی از Supabase برای Auth، PostgreSQL و فضای ذخیره‌سازی خصوصی استفاده می‌کند. رابط سایت می‌تواند روی GitHub Pages بماند و سرویس پشتیبان مستقل باشد؛ در آینده می‌توان رابط را به هاست دیگری منتقل کرد.

## وضعیت و محدودیت مهم

فایل‌های این پوشه و migration در مخزن آماده‌اند، اما تا زمانی که پروژه Supabase واقعی ساخته و کلید عمومی آن در `backend-config.js` تنظیم نشود، ورود و ذخیره‌سازی فعال نخواهد شد. این مخزن به‌تنهایی نمی‌تواند پروژه Supabase یا حساب‌های واقعی را از طرف مالک ایجاد کند. هیچ رمز، service-role key یا توکن GitHub را در فایل‌های عمومی قرار ندهید.

## ۱. ساخت پروژه

1. در https://supabase.com یک پروژه ایجاد کنید.
2. از Project Settings → API، Project URL و publishable key (یا anon key قدیمی) را بردارید.
3. در Auth → Providers مطمئن شوید Email فعال است.
4. در Auth → Settings، ثبت‌نام عمومی (Allow new users to sign up) را غیرفعال کنید؛ حساب‌ها فقط توسط مدیر از داشبورد Supabase ساخته شوند.
5. در SQL Editor محتوای `supabase/migrations/202610240001_admin_backend.sql` را اجرا کنید.
6. در `admin/backend-config.js` فقط Project URL و publishable/anon key را جایگزین placeholderها کنید. این کلید عمومی است؛ service_role key هرگز نباید در مرورگر قرار گیرد.

## ۲. ساخت دو مدیر و کارشناسان

از Authentication → Users در داشبورد Supabase، حساب‌ها را به‌صورت دستی ایجاد کنید. سپس برای هر کاربر، UUID نمایش‌داده‌شده در همان صفحه را در SQL زیر قرار دهید. این SQL را در SQL Editor اجرا کنید؛ آن را در کد فرانت‌اند قرار ندهید.

```sql
-- جایگزین کردن UUIDها با شناسه واقعی حساب‌ها
update public.profiles set role = 'admin', active = true
where id in ('UUID-مدیر-اول', 'UUID-مدیر-دوم');

-- برای کارشناسان نقش پیش‌فرض expert است؛ فعال‌بودن را بررسی کنید
update public.profiles set role = 'expert', active = true
where id in ('UUID-کارشناس-اول', 'UUID-کارشناس-دوم');
```

هر کاربر تازه‌ای که از داشبورد ساخته شود به‌طور پیش‌فرض نقش `expert` می‌گیرد. نقش مدیر را فقط از محیط مدیریتی امن Supabase تعیین کنید. حساب مدیر را به‌عنوان حساب کارشناس استفاده نکنید.

## ۳. مجوزها و ذخیره فایل

- کارشناس می‌تواند مقاله خودش را با وضعیت پیش‌نویس/در انتظار بررسی ثبت کند و فایل را در پوشه مخصوص شناسه خودش بارگذاری کند.
- انتشار نهایی و مدیریت تنظیمات فقط برای نقش `admin` مجاز است.
- جدول‌ها از Row Level Security استفاده می‌کنند؛ مخفی‌کردن دکمه در رابط کاربری به‌تنهایی کنترل امنیتی محسوب نمی‌شود.
- فایل‌ها در bucket خصوصی `rls-editorial` نگهداری می‌شوند؛ حداکثر حجم تنظیم‌شده ۲۰ مگابایت است و نوع فایل‌ها به PDF/JPEG/PNG/WebP محدود شده است.
- فایل‌های منتشرنشده عمومی نیستند. برای انتشار فایل PDF عمومی باید endpoint امنِ امضای URL یا سیاست انتشار جداگانه طراحی شود؛ bucket را صرفاً برای راحتی public نکنید.

## ۴. آدرس پنل و ورود

پس از تنظیم پروژه و انتشار فایل‌ها از طریق GitHub Pages:
- ورود: `/admin/login.html`
- پنل: `/admin/panel.html`

در صورت فعال‌بودن MFA در Supabase، حساب‌های مدیر را به MFA مجهز کنید. از گذرواژه‌های یکتا و قوی استفاده کنید و حساب‌های مدیر را با ایمیل‌های تحت کنترل نشریه بسازید.

## ۵. نکات استقرار و انتقال آینده

- فقط URL و publishable/anon key در فرانت‌اند مجازند؛ service_role، رمز پایگاه داده و توکن GitHub باید محرمانه بمانند.
- برای دامنه سفارشی و Redirect URLs، آدرس واقعی GitHub Pages یا دامنه سایت را در Supabase Auth → URL Configuration اضافه کنید.
- در این نسخه فرم ثبت مقاله و نمایش خلاصه فهرست به backend متصل شده‌اند. پیش از استفاده عملیاتی، تست نقش‌ها، بارگذاری فایل، بازبینی و انتشار را در یک پروژه آزمایشی انجام دهید.
- اطلاعات محرمانه داوری یا نسخه‌های منتشرنشده را در مخزن عمومی GitHub commit نکنید.
